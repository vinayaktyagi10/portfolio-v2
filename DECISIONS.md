# Decisions

## 2026-09-06 — Stack: React + Vite + Framer Motion
**Chose:** React 19 + Vite, with Framer Motion for both the scroll-linked mesh and the panel mount/unmount.
**Why:** The deciding factor is panel state, not the mesh. Per-project open/close state, focus trapping, an Escape handler, a `prefers-reduced-motion` branch, and a mobile/desktop mechanic switch all have to be coordinated; that is what React's component model is for. Framer Motion covers `useScroll`/`useTransform` and `AnimatePresence` in one library, so the scroll driver and the panel transitions share one mental model.
**Alternative considered:** Plain HTML/CSS/JS. Rejected because it means hand-rolling the panel state machine and its cleanup.
**My answer before seeing yours:** React + Vite + Framer Motion, for the reasons above.

## 2026-09-06 — Scroll driver: Framer Motion motion values, not CSS scroll timelines or a hand-rolled listener
**Chose:** `useScroll` + `useTransform`, writing only `transform`/`opacity` through `style={{ x, y }}` on `motion.div`s. Per-node stagger is expressed as a different input range per node (`DELAY` in `src/mesh.js`).
**Why:** Framer batches motion-value writes and applies them as transforms, so the animation stays off layout. Per-node stagger and a dynamically-measured end coordinate are both easy to express as plain numbers.
**Alternative considered:** (a) Native `animation-timeline: scroll()` — runs on the compositor and is the right answer in a vacuum, but browser support is uneven and expressing per-node stagger against a measured DOM target in pure keyframes is awkward. Worth rechecking support before a rewrite. (b) A hand-rolled scroll listener + rAF — easy to accidentally read layout and write style in the same tick and cause forced reflow.
**My answer before seeing yours:** Framer Motion `useScroll`, same reasoning, same two rejections.

## 2026-09-06 — Mesh nodes are absolutely-positioned divs; only the connector lines are SVG
**Chose:** Nodes are real HTML elements in CSS pixel space. A thin SVG overlay strokes the lines between them, reading endpoints from the same `nodePos()` the nodes use.
**Why:** The mesh's resting positions have to agree with the surface rows below. Keeping nodes in the same coordinate space as the document removes the SVG-viewBox-to-CSS-pixel conversion entirely. One position function serves both nodes and lines, so there is no second source of truth to drift.
**Alternative considered:** Authoring the mesh's final layout and the surface layout independently. Rejected — that is precisely how a re-layout jump appears once fonts load or the viewport resizes, and nobody notices until it ships.
**My answer before seeing yours:** Divs for nodes, SVG for lines only, with the resting coordinates measured off the real surface rows.

## 2026-09-06 — Progress is derived from a self-measured runway, not from `useScroll`'s target/offset
**Chose:** `const { scrollY } = useScroll()` (window scroll in px), then `useTransform(scrollY, [0, runway], [0, 1])`, where `runway = revealHeight - stageHeight` measured via `ResizeObserver`.
**Why:** `useScroll({ target, offset })` measures its own ranges from the element and those measurements did not agree with the `svh`-based layout: progress reached 1 roughly 110px of scroll before the sticky stage actually unpinned, so the mesh finished resolving while the surface was still ~110px low, and the crossfade landed misaligned. Deriving progress from the same measured quantity the layout uses makes `p = 1` and "surface top at viewport 0" the same instant by construction. Verified in the browser: at `p = 1` all three node centres match their row dots to the pixel.
**Alternative considered:** Keeping `target`/`offset` and nudging the crossfade window to hide the gap. Rejected — that hides a measurement disagreement instead of removing it, and it would drift again on any layout change.
**My answer before seeing yours:** n/a — this came out of debugging the observed 110px misalignment.

## 2026-09-06 — Row offsets are measured relative to the surface section, not the viewport
**Chose:** Each row dot's position is measured as an offset from the surface section's own top-left. The surface's live viewport position during the pinned range is added back analytically as `(1 - p) * runway`.
**Why:** `getBoundingClientRect()` is viewport-relative, and the surface is itself scrolling during the unravel, so a measured end value goes stale every frame. The offset from the section's own top edge only changes on resize or font load, so it can be measured once and reused, while the moving part is computed from progress.
**Alternative considered:** Re-measuring the rows on every frame. Rejected — it reintroduces a layout read inside the scroll path, which is the jank the transform-only approach exists to avoid.
**My answer before seeing yours:** Measure the rows and feed them in as the end value — correct in principle; the anchoring to the section's own top edge was the correction.

## 2026-09-06 — The surface rows are the only interactive target; mesh nodes are inert
**Chose:** The stage is `aria-hidden` and `pointer-events: none`. Clicking or keyboard-activating a project happens on the real `<button>` row underneath, which the node has crossfaded into.
**Why:** The node and the row occupy the same coordinates at rest, so making both interactive means two handlers and two focus stops for one thing. Keeping the button as the single target means keyboard focus, `aria-expanded`, and the zoom origin all come from one element.
**Alternative considered:** Making the mesh nodes clickable during the unravel. Rejected as duplicated state for no gain — but this is a UX call worth revisiting if you want the project clickable before the mesh finishes resolving.
**My answer before seeing yours:** n/a — not asked.

## 2026-09-06 — Connector lines update via a motion-value subscription, not React state
**Chose:** `useMotionValueEvent(progress, "change", draw)` writes SVG line attributes directly through refs.
**Why:** Routing 18 line endpoints through React state would re-render the tree on every scroll frame. The subscription writes attributes outside React entirely.
**Alternative considered:** `motion.line` with motion values bound to `x1`/`y1`. Would work, but the explicit `draw()` keeps line and node positions provably derived from the same call.
**Honest weakness:** Setting SVG geometry attributes is not a compositor-only operation the way `transform` is — it repaints the SVG each frame. At 18 hairlines this is not measurable, but it is the one part of the scroll path that is not pure transform/opacity, and it would need revisiting if the mesh grew substantially.
**My answer before seeing yours:** n/a — not asked.

The mesh canvas is a clear, readable dark green (`--mesh-bg: #122018`) with the natural green accent (`#5dcaa5`); the depth panels are colder and more artificial (`--panel-bg: #081416`) with a cyan-leaning accent (`--panel-accent: #4fbfb8`), cooler muted text, and a cooler scrim. ## 2026-09-06 — The scroll lock is refcounted, and panel transitions are serialised
**Chose:** `AnimatePresence mode="wait"`, plus a module-level refcount for the `overflow: hidden` scroll lock instead of save-and-restore.
**Why:** Two panels could briefly coexist — close a panel, then click another project inside the ~420ms exit. The old lock saved the current `overflow` on mount and restored it on unmount, so the second panel captured `"hidden"` as the value to restore and the final close left the page **permanently unscrollable**. Replaying the mount/cleanup order React produces (A.mount, B.mount, A.cleanup, B.cleanup) confirmed it: 2 of 3 sequences ended stuck under the old implementation, 0 under the refcount. `mode="wait"` additionally makes the spec's "only one panel open at a time" structurally true rather than merely true of the state object — verified in the browser, panel count never exceeded 1.
**Alternative considered:** `useIsPresent()` to disable the exiting panel's focus trap and keep transitions overlapping. Would work, but serialising is simpler and the reverse-then-zoom reads correctly anyway.
**Honest weakness:** The overlap window is hard to hit with real input, and the frozen-tab behaviour of the automation made it impossible to observe the unmount live — the refcount was verified against a replay of React's call order, not against the running page.
**My answer before seeing yours:** n/a — found while checking that only one panel can be open.

## 2026-09-06 — Idle drift: a time MotionValue alongside scroll, damped by each node's own journey
**Chose:** `useAnimationFrame` writes elapsed seconds into a `MotionValue`; each node's position is a single `useTransform([progress, time], …)` owned by `<Mesh>`, and both the dots and the connector lines read that same value. Drift amplitude is `1 - t`, where `t` is the per-node eased interpolation parameter already inside `nodePos()`.
**Why:** Time has to be a MotionValue, not state, or the frame loop re-renders the tree every frame and undoes the reason the scroll side uses MotionValues at all. Positions are owned by the parent rather than by each `<Node>` so the lines can read the identical value the dots render from — recomputing `nodePos()` a second time for the lines risks a one-frame lag between a dot and the lines hanging off it, which on a mesh is immediately visible. Verified in the live DOM: all 18 edges sit at exactly 0px from their nodes.
**Divergence — the damping breakpoint:** The brief was to damp over the same `[0, 0.6]` range that governs node interpolation, to avoid a second magic number. There is no `0.6` in the code: nodes interpolate over `[DELAY[i], 1]`, and the surface-tracking term means they keep moving right up to `p = 1` by construction — that is what makes the pixel-exact landing work. Introducing `0.6` would have created exactly the second constant the instruction was trying to avoid. Damping on `t` achieves the stated intent better: no new constant, exactly zero when the node finishes (since `t = 1` at `p = 1` for every node), and drift retires strand by strand as each resolves rather than at one global cliff. The hard-clamp reasoning was right and is preserved — `1 - t` reaches true zero, not an asymptote.
**Measured:** peak displacement 5.6px across the mesh, peak speed 2.7px/s, ~3.2px of movement within the first two seconds, slowest component a 12s period. Landing error at `p = 1` is 0px across five timestamps and all three project nodes; residual drift is 0.15px at `p = 0.86` and 0.007px at `p = 0.95`.
**Bug found while measuring:** The first implementation guarded the drift with `time > 0`, so a node sat on its authored coordinate at first paint and then snapped to its phase offset on the first animation frame — a 230px/s pop on load, which is what the speed measurement caught. Each axis is now measured from its own value at `t = 0`, so every node starts exactly on its tangle coordinate and eases away. Confirmed in the DOM: node 0 renders at 788.43px, its authored coordinate to the pixel.
**Also:** the frame loop returns early when `progress >= 1` or reduced motion is set, so no rAF loop is held open behind the surface once the hero is resolved. `useMotionValueEvent` and a post-render effect cover the cases the loop skips.
**My answer before seeing yours:** Same on all three of the mechanism points — `useAnimationFrame` into a MotionValue, one shared position value per node, hard clamp over asymptote. The damping quantity is where we differed, and only because the range you named was not the one in the code.

## 2026-09-06 — First-paint geometry is measured before render, not corrected after it
**Chose:** `geom` is initialised from `probeStageBox()` — a throwaway element carrying the same sizing as `.stage` (`width: 100%`, `height: 100svh`), measured and removed inside the `useState` initializer before the first render — instead of a hardcoded `{ w: 1200, h: 800 }` corrected in a layout effect. Added `html { overflow-y: scroll }` so the scrollbar gutter exists from the first paint and the probe measures the width the stage will actually have.
**Why:** Framer's derived values do not recompute synchronously. Verified directly in the page: a `transformValue` computes eagerly at creation, but after `src.set(7)` the derived value still read its old result immediately afterwards and 50ms later — it only updates on the frame loop. So a geometry correction applied in `useLayoutEffect` **cannot** reach the DOM before the first paint, no matter how early it runs. The instrumented load confirmed it: values at `a_firstRender`, `b_afterMeasure` (still inside the layout effect) and `c_passiveEffect` (after paint) were all identical and all wrong.
**Measured, same category as the idle-drift fix — rendered pixel position at first paint vs. authored t = 0 coordinate:**
- Before: node 0 painted at x=484.8 against an authored 788.43 (**303.6px** error); node 4 at 812.4 against 1321.21 (**508.8px**). 484.8 is exactly `0.404 x 1200` — the hardcoded default. The whole mesh painted at the wrong scale, then jumped.
- After: max error **0.0038px** across all ten nodes, and the first-paint transform string is byte-identical to the settled one. All 18 connector lines carry geometry at first paint; none render attribute-less.
**On the verification method:** CPU/network throttling was not reachable through this tooling, but the automation runs the page in a backgrounded tab, which pauses `requestAnimationFrame` entirely. That is a strictly harsher version of the same test — it makes the window between first paint and first animated frame unbounded rather than merely long, which is how a 303px error was observable at all instead of flashing past in 16ms.
**My answer before seeing yours:** n/a — audit you asked for; the pre-render probe was mine.

## 2026-09-06 — Scroll-restored reloads still pop, and the mitigation was reverted
**Found:** Reloading part-way down the hero paints the mesh at its fully tangled `p = 0` state and then snaps to the restored scroll position on the first animated frame. Measured at up to **639.9px** for the worst node, from 444px of restored scroll. The first paint is not *wrong* — it is correct for `scrollY = 0` — but the browser then scrolls underneath it.
**Not fixed, deliberately.** Two mitigations were built and measured, and both failed:
1. Seeding `scrollY.set(window.scrollY)` during render, before the transforms are created. Did not change the painted frame.
2. Hiding the stage for one frame when the layout effect sees a non-zero scroll position. The probe showed the stage still `visible` at `c_passiveEffect_afterPaint` — the hide lands *after* paint too, so it would flash the mesh, hide it, then reveal it. Strictly worse than doing nothing.
Both were reverted rather than shipped. The root cause is that every correction path runs after the paint that needs correcting.
**The fix that would work** is `history.scrollRestoration = "manual"`, so the page always loads at the top. For a site whose whole premise is a scroll-linked reveal from the top, restoring the user mid-unravel is not a meaningful state — but it also means a refresh loses your place in the experience and contact sections. That is a product call, so it is left open.
**Honest weakness:** the browser window kept resizing between measurements in this environment, which corrupted several intermediate readings before it was spotted. The numbers above are from runs where the stage box was identical at probe time and at settle time.
**My answer before seeing yours:** n/a.
