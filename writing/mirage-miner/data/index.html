What an SSH honeypot's logs led to: data and method

The full numbers behind the story.

Written 2026-10-11, last updated 2026-10-11·

This post is about data from my own SSH honeypot, Mirage. Attacker and payload addresses are defanged (hxxp, [.]). No malware samples are published, only hashes.

Status of this draft (2026-10-11). Every number comes from frozen data: the Frankfurt-era backup and a Nuremberg export cut at 2026-10-10 22:54:06 UTC. Queries 01 to 03 are mine; the other queries (adhoc_checks.sql) were written by an AI assistant. Its host table matches the output of my own queries 02 and 03; the other numbers from it (the SSH/Telnet split, the IP overlap, the failure counts) I have not re-derived myself. Everything is dated in UTC.

Summary

I run an SSH honeypot called Mirage. Looking for the payloads attackers tried to download, I found one server handing out a loader script and an XMRig-based cryptocurrency miner. The strings and algorithm names point to Monero, but I did not find the pool or the wallet. I fetched them through Tor into an isolated VM and took them apart without letting them reach the network.

  • The obvious filter for downloads (parsed_command equal to wget or curl) caught 0 of the 39 sessions in the first dataset that tried to download something (each had one command line containing a URL), because that column holds only the first word of the line.
  • The miner renames itself to nginx: worker process, replaces the crontab with an @reboot entry, and tries to resolve its pool with DNS-over-TLS against 13 hard-coded resolvers (11 well-known public ones and 2 ISP addresses of unknown owner).
  • 49.5% of the SSH source IPs in the second dataset tried a URL fetch, but one campaign accounts for almost all of it: without that campaign, 43 of the remaining 456 IPs (9.4%) did. The two datasets are different sensors and windows, so I do not read the gap to the first dataset's 2.7% as a trend.
  • Not established: the mining pool, the wallet, whether the SSH client inside the binary spreads it, and what the binary-scanning is for.
  • The files are what a Tor exit was served on 2026-10-10; the operator may serve something different to real victims.

1. Data and scope

I applied to Google Summer of Code with the Honeynet Project and was not selected, but I was curious how honeypots actually work. Over the summer my friend Devang and I decided to build one together: Devang brought the ML side and I brought the infrastructure side, and the result is Mirage. We built it mainly to learn and experiment. This write-up is the first time I have gone through what it captured myself, to find out what attackers actually do and what I can learn from it.

Mirage is an SSH honeypot written in Go. It accepts some weak logins, gives the attacker a fake Ubuntu shell built from a fixed list of commands, and records each session and each command line in Postgres. From 2026-09-29 a Telnet sensor runs beside it. A randomized hardware-deception experiment, assigned per source IP, started on 2026-09-27; I did not split any result below by experiment arm.

3. Finding the payload URLs

My first idea was to filter on parsed_command for wget or curl. That found nothing, because parsed_command holds only the first word of the line, and these lines start with cd or uname with the wget further along. The full line is in raw_input_b64, so I searched that for http:// or https:// anywhere instead. My first attempt at that returned 0 rows because the column is base64, and I had to decode it before searching.

  • parsed_command is the first whitespace-separated word of the whole payload (strings.Fields(payload.Command)[0] in server.go).
  • Result: 39 sessions in dataset A contain a URL, one command line each (95 URL mentions in all); the wget/curl filter matches 0 of them.
  • Extraction: every https?://… match per command row, stopped at whitespace and ' " < > ) ;, grouped by host with distinct sessions and distinct source IPs (queries 02 and 03). Joining to sessions lost no URL rows (95 of 95 in A, 1,646 of 1,646 in B).

4. Fetching safely

This was my first time handling malware, and I learned most of it with an AI assistant's help. I made the setup safe in layers. The files were fetched through Tor, so my home IP address is never exposed. They were fetched inside a VM that has no access to my machine or the home network, and firewall rules stop it from talking to anything else. Before running anything I took a snapshot I could return to if something went wrong. I fetched with plain downloads only (no execution), then looked at the files with strings, file and similar tools to see what they were.

  • Local QEMU/KVM VM (Debian 13), no shared folders, clipboard channel, USB redirection, sound or guest-agent channel.
  • Network: an isolated libvirt network (no forward element, 192.168.77.0/24). Host firewall (nftables): from the VM bridge, accept TCP 9050 only, drop everything else; drop forwarding in both directions. One ufw rule allows that same port, because ufw's default deny is a separate chain and an accept in one chain does not override a later drop.
  • Egress: Tor SOCKS on the host, bound to the bridge address only. curl --socks5-hostname so Tor resolves names.
  • Rules: plain GET only; no probing; no executing during the fetch stage; no use of the credential embedded in one script; --max-filesize, --max-redirs 0, output to a file with the execute bit off.
  • Isolation tests from inside the VM: via Tor IsTor: true; curl http://1.1.1.1 fails at once (no route); the host's Grafana port times out.
  • Snapshots: clean-base (no samples) and pre-exec (samples fetched and unpacked, nothing executed). After the one run of the miner I killed it, powered the VM off and reverted it to pre-exec, which also removed the @reboot crontab entry it had installed.

Loader (read, not run) — observed: random hidden file name; downloads stages from the same server over HTTPS with certificate checks off; finds a writable directory by writing 2 MB; runs clean; chooses a binary by uname -mp (x86_64, i686, aarch64, armv7, riscv; tries all five if none matches); runs it with the first argument. The server's Last-Modified for the loader was 2026-10-03, the same day that host first appeared in my data.

clean — observed: removes immutable flags and then deletes lines matching wget|curl|/dev/tcp|/tmp|\.sh|nc|bash -i|sh -i|base64 -d from crontabs and shell profiles; stops c3pool_miner and bot.service; empties /tmp, /var/tmp, /dev/shm. The filter is crude (nc matches any line containing those two letters).

Miner, static — observed: UPX-packed (marker present), statically linked; after unpacking, XMRig strings (XMRIG_* names and the donation hosts donate.v2.xmrig.com and donate.ssl.xmrig.com), RandomX algorithm names, stratum+tcp:// and stratum+ssl://%s (the pool address is filled in at runtime), libssh2 symbols, reads of CPU, GPU, hugepage and DMI information. No wallet and no config file found.

Miner, dynamic (one run, VM link down, strace -f) — observed:

  • forks and calls setsid(), renames itself, shows in ps as nginx: worker process. /proc/PID/exe points to the sample; nginx is not installed.
  • runs crontab -r, then installs @reboot <path to itself>.
  • repeatedly opens /proc/, resolves each process's executable and reads it.
  • tries TCP port 853 (DNS over TLS) on 13 hard-coded addresses in a tight loop with no backoff (about 1.3 million failed attempts in roughly six minutes). Eleven are public resolvers: Cloudflare 1.1.1.1 and 1.0.0.1, Google 8.8.8.8 and 8.8.4.4, Quad9 9.9.9.9, an address registered to IBM in Quad9's neighbourhood (9.9.10.10), Njalla (95.215.19.53) and four OpenNameServer nodes (217.160.70.42, 213.202.211.221, 81.169.136.222, 185.181.61.24). Two are ISP addresses whose owner I could not identify (80.152.203.134, 109.91.184.21).
  • all connections failed with "network unreachable", so nothing left the VM.

Inferred (label as such): a watchdog (kill(pid, 0) on the main process); the CPU load seen was the DNS retry loop, not hashing; the resolver list exists so the miner can still find its pool when plain DNS (port 53) is blocked. The clean script is a competitor killer: it stops c3pool_miner and bot.service and strips matching lines from crontabs, so other miners and bots go before this one runs. That is my reading of what it does; the script does not say so. XMRig and RandomX point to Monero mining, but without a pool or wallet I cannot confirm which coin.

Not established: pool hostname, wallet, whether the SSH code spreads the miner (present in the binary, not exercised), purpose of the process and binary scan, any family name (the loader contains the string "redtail", weak evidence on its own), and whether real victims receive the same files.

What these taught me about method: measure the thing itself and not a stand-in; write down the definition next to the number; check which sensor and protocol a symptom lives on before reading code; and when one bot is most of a count, say so and show the count without it.

7. Further hardening of Mirage

Reading what attackers did with Mirage's answers showed where it behaved unlike a real Ubuntu host. There are three versions of the sensor in this post: v1 is every version before the first deploy: dataset B was captured by several earlier versions of the same code (the sensor was deployed on 2026-08-30 and updated on 09-05, 09-09, 09-11 and 09-29; a1d60d1 ran from 2026-09-29 to the deploy), and dataset A came from an earlier sensor generation whose code version I did not check; v2 (2248461, 12 commits) went live on 2026-10-10 at 22:54:06 UTC; v3 (9ed852e, 4 commits) on 2026-10-11 at 07:57:17 UTC.

What I can and cannot say. The v2 window is 9 hours: 3,111 SSH sessions, but only 285 SSH command rows from 12 source IPs (Telnet: 279 sessions, 2,817 rows). In that window the failures I had fixed did not recur. That shows the commands now answer; with 12 IPs it does not show the fixes cover what attackers will try next, and it does not show whether attackers behave differently. wget and curl after the fix have not been exercised by a real attempt yet.

What is still untested. v3 (for loops, ping, perl, echo -e) is deployed and I expect it to close the gaps above, but I have not measured it, and v2 itself is thinner than I would like. I will rerun the same checks on the v3 window in three to four days (around 2026-10-14 or 15) and update this post with whether the fixes held.

Fingerprinting. Describing exactly how a honeypot answers wrongly helps the next person recognise it. I describe the gap classes and leave out the exact reply strings.

8. Detection ideas and indicators

  • Masquerade. Alert when a process named nginx: worker process has a /proc/PID/exe that is not an nginx binary. Test: in a lab VM, run any harmless program that renames itself to nginx: worker process and check that the rule fires, and that a real nginx does not trigger it.
  • DNS-over-TLS from a host that never uses it. Alert on outbound TCP 853 from hosts with no resolver configured for DoT. Test: in a lab, send TCP 853 traffic from a plain host and from one configured for DoT.
  • Crontab replacement. Alert on crontab -r followed within seconds by crontab - that installs an @reboot entry pointing into a non-standard directory. Test: replay the pair in the lab and compare with a normal crontab -e.

9. Limits and what I would do next

  • One fetch per URL, through Tor; no check that victims get the same file.
  • Session counts are inflated by a few bots; the unit is the source IP, and an IP is not an actor.
  • Dataset B mixes SSH and Telnet. I split the key numbers by protocol; the URL host table still includes Telnet sessions where marked.
  • Experiment arms are not accounted for.
  • v2 evidence is thin (12 SSH source IPs in nine hours) and v3 is unmeasured.
  • Next: measure v3 over several days; recover the pool by running the miner against a fake resolver I control; fix the Telnet quoting and the invalid-UTF-8 save error; re-measure.
  • Later: turn this investigation into a pipeline. New captured payloads would be handed to the isolated VM automatically, analyzed (static first, then a controlled run), and summarized into a short report. A person reviews it in 15 to 20 minutes and approves, rejects or edits it before anything is published. The automatic part never executes a sample outside the VM and never publishes by itself.
