What an SSH honeypot's logs led to: from a payload URL to a cryptocurrency miner

Written 2026-10-11, last updated 2026-10-14·

This post is about data from my own SSH honeypot, Mirage. Attacker and payload addresses are defanged (hxxp, [.]). No malware samples are published, only hashes.

Why I built Mirage

I applied to Google Summer of Code with the Honeynet Project and was not selected, but I stayed curious about how honeypots actually work. Over the summer my friend Devang and I decided to build one together. Devang brought the ML side and I brought the infrastructure side, and the result is Mirage, a honeypot written in Go. We built it mainly to learn and experiment.

This write-up is the first time I have gone through what Mirage captured myself. I wanted to find out what attackers actually do once they get a shell, and what I could learn from it. One thing to keep in mind from the start: a row in the logs is one command line, a session is one connection, and a source IP is one address. They are different counts, and a source IP is still not an actor.

The filter that found nothing

My first idea was simple. To find the malware attackers tried to download, I would look for commands that start with wget or curl. That found nothing: 0 of the 39 sessions in the first dataset that tried to download something. Each of those sessions had one command line containing a URL.

The reason is that Mirage stores a field called parsed_command, and it holds only the first word of the line. These lines started with cd or uname, with the wget further along. The full line is in another column, raw_input_b64, and my first search of that found nothing either, because the column is base64. I had to decode it before searching. Once I searched the decoded text for http:// or https:// anywhere in the line, the URLs appeared.

What I took from it is to check what a column actually contains before trusting a filter built on it.

What the URLs showed

In the first dataset, 4 of 146 source IPs (2.7%) tried a URL fetch. In the second dataset, from a different sensor and period, it was 49.5% of SSH source IPs, but almost all of that comes from one campaign. Take that campaign's 362 IPs out of both the count and the total, and 43 of the remaining 456 IPs (9.4%) tried a fetch. The two datasets are different sensors and windows, so I do not read the gap as a trend.

Before the URLs, the commands themselves looked like hardware recon: CPU count, memory, PCI devices, GPU. That fits a miner operator checking what a host is worth, but it is a hypothesis; the commands alone do not show intent.

One payload server, 217.60.195[.]113, showed up in both datasets, weeks apart, on sensors that did not run at the same time. That is not geographic targeting. One source IP used it in both, but the same address is not proof of the same actor. The server I actually fetched from, a different one, first appeared in my data on 2026-10-03, the same day as the loader's Last-Modified date.

Fetching the files safely

This was my first time handling malware, and I learned most of it with an AI assistant's help. I made the setup safe in layers.

Everything was downloaded through Tor, so my home IP address was never exposed. The downloads happened inside a virtual machine with no route out. Firewall rules stop it from talking to anything except the Tor port, and it has no shared folders or clipboard with my machine. I fetched with plain downloads only: nothing was executed during the fetch, and the files were saved without the execute bit. Before running anything I took a snapshot I could return to if something went wrong.

Then I looked at the files with strings, file and similar tools to see what they were. When I did run the miner, I ran it inside the VM with its network link down, and restored the snapshot afterwards.

What the miner did

The server handed out a loader script, a cleanup script and a UPX-packed miner built on XMRig.

The loader picks a random hidden file name, finds a writable directory, downloads the other pieces over HTTPS with certificate checks off, picks a binary to match the machine's architecture, and runs it. The cleanup script, clean, deletes crontab and shell-profile lines matching a list of patterns, stops two named services (c3pool_miner and bot.service) and empties /tmp, /var/tmp and /dev/shm. I read it as a competitor killer that removes other miners and bots before this one runs. That is my reading; the script does not say so.

I ran the miner once, in the VM with its network link down, under strace. What I observed: it forked and renamed itself so that ps showed nginx: worker process, although nginx is not installed and /proc/PID/exe pointed to the sample. It ran crontab -r and then installed an @reboot entry pointing at itself. And it tried TCP port 853 (DNS over TLS) on 13 hard-coded addresses in a tight loop with no backoff, about 1.3 million failed attempts in roughly six minutes. Eleven of those addresses belong to well-known public resolvers; two are ISP addresses whose owner I could not identify. All the connections failed, so nothing left the VM.

What I infer, and did not directly see: a watchdog that checks the main process is still alive; that the CPU load I saw was this retry loop and not hashing; and that the resolver list exists so the miner can still find its pool when plain DNS on port 53 is blocked.

What I still don't know

There is a lot I did not find. I call it a cryptocurrency miner because the binary is an XMRig build with RandomX algorithm names. XMRig and RandomX point to Monero, but I did not find the pool or the wallet, so I cannot confirm which coin. I also do not know:

  • the mining pool or the wallet;
  • whether the SSH code inside the binary spreads it (it is there; I did not exercise it);
  • what the process and binary scanning is for;
  • the family name (the loader contains the string "redtail", which is weak evidence on its own);
  • whether real victims receive the same files. What I have is what a Tor exit was served on 2026-10-10.

What I got wrong

I got several things wrong along the way, and these are the ones I learned the most from.

About 5 of the 39 URL-bearing sessions would parse as wget/curl0

Mirage splits quoted multi-line strings into separate commands (SSH)The SSH splitter is quote-aware. The 21 UserKnownHostsFile: command not found sessions are on Telnet, where every line the bot sent was logged and answered as its own command. I had read the wrong sensor's code
One headline percentage describes the whole dataset49.5% falls to 9.4% (43 of 456 IPs) without one campaign, and the datasets mix SSH and Telnet

What these taught me about method: measure the thing itself and not a stand-in; write down the definition next to the number; check which sensor and protocol a symptom lives on before reading code; and when one bot is most of a count, say so and show the count without it.

What I fixed, and what's next

Reading what attackers did with Mirage's answers showed where it behaved unlike a real Ubuntu host. Commands such as sh, rm, case and for answered "command not found". I fixed these in two rounds: the first (v2) went live on 2026-10-10 at 22:54:06 UTC, and the second (v3) on 2026-10-11 at 07:57:17 UTC.

The evidence for the fixes is thin. The v2 window is 9 hours, with commands from only 12 SSH source IPs. In that window the failures I had fixed did not come back. That shows the commands now answer. It does not show the fixes cover what attackers try next, and it does not show that attackers behave differently.

I measured v3 on 2026-10-14, after about 68 hours: none of the commands I had fixed answered "command not found" any more. That is still thin evidence. perl came from one IP, every ping was bare with no address, and new gaps showed up, such as nproc and uptime. Whether attackers stay longer is not measured. The details are in section 7 of the data page. I leave out the exact reply strings, because describing exactly how a honeypot answers wrongly helps the next person recognise it.

Next, I want to fix the invalid-UTF-8 save error on Telnet first (1 lost session in v2, 31 in v3), then add the missing commands, then work on the Telnet quoting. I also want to run the miner against a fake resolver I control to try to recover the pool. Later, I want to turn this investigation into a pipeline where a person reviews and approves the findings in 15 to 20 minutes before anything is published. The automatic part would never run a sample outside the VM and never publish by itself.
